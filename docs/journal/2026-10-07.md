# 2026-10-07: NFS share on db2, autofs on db1

I wanted the backups off db1. They now go to db2 over NFS, and a restore from there gave the same 10000 rows. Then I filled `/pgdata` on purpose to see an INSERT fail, and a few minutes later PostgreSQL crashed on its own, with nobody writing.

Phase 1 · Docs: [NFS share](../architecture/nfs.md), [Backups](../architecture/backups.md), [ADR 0006](../decisions/0006-autofs-for-the-nfs-share.md) · Runbook: [Grow a data volume while PostgreSQL runs](../runbooks/grow-a-data-volume.md) · Checks: [09](../../checks/09-backup.sh), [10](../../checks/10-nfs.sh)

## What I did
- Gave db2 its own tuned profile, `virtual-guest-lab`, so `tuned-adm verify` passes there too.
- Checked that `postgres` (UID 26) and `dba` (GID 2000) match on both hosts. NFS sends numbers, not names.
- Added a 10 GiB data disk to db2, with LV `backup` (3 GiB) on `/srv/backup`.
- Exported `/srv/backup` to db1 only. `root_squash` stopped root, and `postgres` could write.
- Mounted it on db1 with autofs and pointed `pg-backup.service` there. A restore from db2 matched the fingerprint.
- Added `checks/10-nfs.sh`. It passed after a reboot of both hosts.
- Filled `/pgdata` with `fallocate`. An `INSERT` failed with `No space left on device` and was rolled back.
- Grew LV `pgdata` from 5 to 7 GiB while PostgreSQL ran, and my `psql` session stayed connected.
- Cleaned up, rebooted db1 and ran checks 05, 06 and 09. Check 05 now expects 7 GiB.

## What broke
- **PostgreSQL crashed while nobody was writing.** Autovacuum and the next checkpoint need new files, and the checkpoint ended in `PANIC`. It was back in a second with no data lost, but `systemctl status` still said "active": only the PostgreSQL log showed the crash.
- **`mount -t nfs`: `NFS: mount program didn't pass remote address`.** db1 had no `nfs-utils`, so no `mount.nfs`. The message never says that.
- **`lvs` showed 6 GiB, but `df` still saw 5 GiB.** `lvextend` without `-r` grows only the LV, and the file system needs `xfs_growfs` too.
- **`RequiresMountsFor=` does not work for an autofs path.** systemd knows only fstab and mount units, so the service waits for `autofs.service`.
