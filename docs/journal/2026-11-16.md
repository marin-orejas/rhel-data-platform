# 2026-11-16: Kubernetes cluster and a Deployment

I wanted the cluster built by kubeadm from a config file in the repo, then an app on it as a Deployment. Now three nodes are `Ready` on 1.36.6, two httpd pods run on the workers, and checks 26 and 27 pass after a reboot of all three nodes. Right after `kubeadm init`, k8s1 was `NotReady` and coredns `Pending`, but nothing was broken: the node had no CNI config until Calico wrote one. Later a version with a bad readiness probe stalled, and both old pods stayed `Ready` until I rolled it back.

## What I did
- Copied the four hand files of lesson 25 into `kubernetes/nodes/` under their host paths. Same sha256 on all three nodes.
- `kubernetes/kubeadm/config.yaml` pins `v1.36.6`, sets the pod subnet `10.244.0.0/16` and adds `127.0.0.1` to the API cert.
- Copied the k8s1 disk first, then `kubeadm init --config` with `--skip-token-print`, so no token went into the output.
- Kept firewalld, though the Calico docs say to turn it off. The base role trusts `10.244.0.0/16` and opens `5473/tcp`.
- Calico v3.33.1 through the Tigera operator, VXLAN with BGP off, nftables. k8s1 went `Ready` about a minute later.
- Joined k8s2 and k8s3 with a 1 h token, then deleted both bootstrap tokens. The one from `init` was still there.
- `kubectl` 1.36.6 on the desktop, through `ssh -N -L 6443:192.168.122.21:6443 nuc`. A pod on k8s2 got `smoke-b` from one on k8s3.
- Check 26 reads the cluster with `kubectl` and the nodes through Ansible. A test line in `k8s.conf` on k8s3 gave one FAIL.
- A bare pod from `kubectl run` stayed gone after `kubectl delete`. A pod of the Deployment came back in seconds with a new name.
- `kubernetes/apps/web/` has the namespace and a Deployment of two httpd pods from UBI 10, on `10.2-1794215538` first.
- Idle httpd used about 17 MB in `crictl stats`. Requests are `50m` and `64Mi`, limits `250m` and `128Mi`.
- With the readiness probe on `/` the new pod stayed `0/1`, because `/` answers `403`. Both probes ask for `/.noindex.html` now.
- Moved to `10.3-1793879148` with `maxSurge: 1` and `maxUnavailable: 0`, one new pod at a time.
- A readiness probe on `/healthz`, set only on the live object, stalled the rollout. After 120 s: `ProgressDeadlineExceeded`.
- Check 27 has 14 checks through the tunnel. `kubectl scale --replicas=3` gave exactly one FAIL, the diff with the file.
- A reboot of all three nodes left the pods with their names and IPs, and `RESTARTS 1`. So check 27 looks at `Ready`.

## What broke
- **`kubectl describe pod -n kube-system -l k8s-app=kube-dns | grep -A4 '^Events:'` printed nothing.** kubectl 1.36 shows events only when it describes one object, and the selector matched two pods. One pod by name, or `kubectl get events -n kube-system`.
- **coredns stayed `Pending` with `0/1 nodes are available: 1 node(s) had untolerated taint(s)`.** The message doesn't name the taint. The node had `node.kubernetes.io/not-ready:NoSchedule`, and coredns tolerates `not-ready` only as `NoExecute`. It went away with Calico.
- **`openssl: command not found` on k8s1.** The clones of `rhel-base` have `openssl-libs` but not the tool. I installed it by hand to read the API cert, then put it into the base role.
- **`kubectl rollout undo` warned that the Deployment is managed with `kubectl apply`.** Undo changes only the live object, not the file or its `last-applied-configuration`. Here the file already held 10.3, and after a bad version from the file the fix is the file and a new `apply`.
