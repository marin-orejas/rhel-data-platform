# 2026-10-05: PostgreSQL on port 5433, tuned and the dba group

I moved PostgreSQL to port 5433 and let db2 connect. That meant four locks on db1: firewalld, SELinux, `listen_addresses` and `pg_hba.conf`, and each one gives its own error on db2. I also made a tuned profile for db1 and the `dba` group with a shared directory.

Phase 1 · Docs: [PostgreSQL on db1](../architecture/postgresql.md), [Tuning](../architecture/system.md#tuning), [DBA group](../architecture/system.md#dba-group-and-shared-directory) · Checks: [07](../../checks/07-postgres-remote.sh), [08](../../checks/08-tuned-dba.sh)

## What I did
- Wrote down the starting state first: listening ports, SELinux port types, the firewall zone and the PostgreSQL settings.
- Set `port = 5433` with `ALTER SYSTEM`, restarted, found the AVC and gave the port `postgresql_port_t` with `semanage port -a`.
- Opened `5433/tcp` on db1 and set `listen_addresses = '*'`.
- Created the role `remote_test` and one `pg_hba.conf` line for it from db2 with `scram-sha-256`. The password is in `~/.pgpass` on db2.
- Set `PGDATA` and `PGPORT` in the postgres user's `.bash_profile`. After a reboot, db2 connected with no change. Added `checks/07-postgres-remote.sh`.
- Made my own tuned profile, `postgresql-guest`: `postgresql` without `boost` and `[scheduler]`, so `tuned-adm verify` passes.
- Created the group `dba` (GID 2000) on both hosts and `/srv/dba` with setgid and a default ACL. Added `checks/08-tuned-dba.sh`.

## What broke
- **Each lock gives its own message on db2**, so the message tells which one is closed:

| Message on db2 | What closed it |
|---|---|
| `No route to host` | firewalld on db1, although `ping` and `ssh` worked |
| `Connection refused` | nothing listens on that address |
| `FATAL: no pg_hba.conf entry ...` | PostgreSQL itself |
| `FATAL: password authentication failed` | wrong password |

- **After the port change the server did not start, and the journal did not say why.** The PostgreSQL log had `could not bind ... Permission denied`, and on a port above 1024 that points to SELinux.
- **`usermod -G` without `-a` replaces all supplementary groups**, and would take away `wheel` and with it sudo. I test in a new session before closing the old one.
- **psql asked for the password and gave no warning.** `sudo vim ~/.pgpass` had made the file owned by root, so my user could not read it.
