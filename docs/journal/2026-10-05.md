# 2026-10-05: PostgreSQL on port 5433, tuned and the dba group

## What I did
- Moved PostgreSQL on db1 to port 5433 and let db2 connect. A connection has to pass four things on db1: firewalld, SELinux, `listen_addresses` and `pg_hba.conf`.
- Wrote down the starting state first: `ss -tlnp`, `semanage port -l`, `firewall-cmd --info-zone=public`, and the views `pg_settings` and `pg_hba_file_rules`.
- Set `port = 5433` with `ALTER SYSTEM`. It writes to `postgresql.auto.conf`, so `postgresql.conf` stays as `initdb` made it. `pg_file_settings` shows what is in the files before a restart.
- Restarted on purpose before the SELinux change to see the failure. Found the AVC with `ausearch -m AVC -ts recent` and gave the port the type `postgresql_port_t` with `semanage port -a`.
- Opened `5433/tcp` in the `public` zone on db1: `--permanent`, then `--reload`, then checked both the runtime and the permanent list.
- Set `listen_addresses = '*'` and restarted. The server now listens on `0.0.0.0:5433` and `[::]:5433`.
- Created the role `remote_test` (login only), set its password with `\password`, and added one line to `pg_hba.conf` for it from db2's IP with `scram-sha-256`. Checked the file with `pg_hba_file_rules` before `systemctl reload`.
- Installed only the client, `postgresql18`, on db2 and saved the password in `~/.pgpass` (mode 600).
- Set `PGDATA` and `PGPORT` in the postgres user's `.bash_profile`, so `psql` and `pg_ctl` work without options.
- Rebooted db1. db2 connected without any change on db1. Added `checks/07-postgres-remote.sh`. It runs on db2, and I tested that it fails when `.pgpass` has the wrong mode.
- Installed `tuned-profiles-postgresql` on db1 and compared its profile with `virtual-guest`. `virtual-guest` changes only `vm.swappiness` and the dirty page limit, and `postgresql` overrides both, so merging the two profiles would change nothing.
- Made my own profile, `postgresql-guest`, in `/etc/tuned/profiles/`. It includes `postgresql`, drops `boost` from `[cpu]` and turns off `[scheduler]`. `tuned-adm verify` passes, also after a reboot.
- Measured the idle VMs on the NUC with `top`: db1 with the new profile and db2 with `virtual-guest` both use 0.2% CPU, so `force_latency=1` has no visible cost.
- Created the group `dba` with GID 2000 on db1 and db2 and added myself with `usermod -aG`. The GID is fixed because NFS compares numbers, not names.
- Created a temporary user, `dba_test`, set password aging and an account expiry date with `chage`, and gave it `umask 027` in its `.bashrc`. At the end I deleted it with `userdel -r` and removed the files it left outside its home.
- Found out where my umask comes from: no file sets it. The shell inherits `0022` from `sshd`.
- Created `/srv/dba` (`root:dba`, `2770`) with a default ACL for `dba`. New files get the group `dba`, and the group can write them whatever the umask is.
- Added `checks/08-tuned-dba.sh`. It runs on both hosts, and I tested that it fails without the setgid bit.

## What broke and how I fixed it
- Each lock gives its own error on db2, so the message tells which one is closed:

| Message on db2 | What closed it |
|---|---|
| `No route to host` | firewalld on db1. It rejects the packet with ICMP. Not a routing problem: `ping` and `ssh` worked. |
| `Connection refused` | Nothing listens on that address. The kernel on db1 answers, and PostgreSQL never sees the connection. |
| `FATAL: no pg_hba.conf entry ...` | PostgreSQL itself. Messages with `FATAL:` come from the server. |
| `FATAL: password authentication failed` | Wrong password |

- The same message after a change means the same lock. I first opened the port on db2 instead of db1, and the error did not change. Incoming traffic is filtered on the server. I closed the port on db2 again.
- After the port change the server did not start, and the journal did not say why. RHEL turns on the logging collector, so the server writes its own log to `/pgdata/pgsql/data/log/postgresql-<day>.log`. The reason was there: `could not bind ... Permission denied`.
- `Permission denied` on a port above 1024 points to SELinux, because Unix only limits ports below 1024. The AVC showed `name_bind` denied for `postgresql_t` on a port of type `unreserved_port_t`.
- `semanage port -a` needs the type after `-t`. Without it, semanage takes the type as the port and reports `unrecognized arguments: 5433`. The usage line and the EXAMPLES at the end of `man semanage-port` show the right form.
- Ports have no `restorecon` step. The port type lives in the policy, so `semanage port` works at once and survives a reboot.
- I installed `postgresql18-server` on db2 instead of the client. `dnf info` shows the summary of each package. `dnf history undo` removed it together with its dependencies. The `postgres` user it created stays.
- After the port change, `sudo -iu postgres psql` looked for `/var/run/postgresql/.s.PGSQL.5432`. The port is part of the socket file name. `PGPORT=5433` in the postgres user's `.bash_profile` fixed it. The same file still had the old `PGDATA`, so `pg_ctl status` did not find the cluster.
- Options before the command name belong to sudo. In `sudo -iu postgres -p 5433 psql`, `-p` is sudo's own option (the password prompt). Right: `sudo -iu postgres psql -p 5433`.
- `sudo vim ~/.pgpass` made the file owned by root. With mode 600 my user could not read it, so psql asked for the password and gave no warning. Files in my own home need no sudo.
- `SHOW data_directory` does not check `PGDATA` in a profile. It asks the server, which gets `PGDATA` from the drop-in. `printenv` as the postgres user shows what the profile sets.
- `tuned-adm verify` failed with the `postgresql` profile. The output only suggests a restart. The reason was in `/var/log/tuned/tuned.log`:
  - `boost`: a VM has no CPU frequency driver. The option comes from `throughput-performance`, so `verify` fails on db2 with `virtual-guest` too.
  - `sched_*`: `Operation not permitted`, even for root. The VMs boot with Secure Boot, so the kernel runs in lockdown mode (`integrity`) and blocks `debugfs`. I did not turn off Secure Boot for two old scheduler settings.
- `man tuned.conf` lists only `replace=`, but `drop=` and `enabled=false` also work in tuned 2.27.
- I copied the comments from the example profile into my own. The profile worked, but the comments were wrong. A wrong comment is worse than none.
- `top -p "$(pgrep -f guest=db1)"` gave `-p argument missing` on db1: the QEMU process runs on the NUC, so `$(...)` was empty. When a command with `$(...)` fails oddly, run the inner part alone.
- `chage -E 2026-12-31` stored 30 December. chage converts the date in the local time zone (UTC+1), and midnight here is still the day before in UTC. `chage -l` shows the stored date. Fix: give the day number, `$(( $(date -ud 2026-10-31 +%s) / 86400 ))`.
- `usermod -G` without `-a` replaces all supplementary groups and would take away `wheel`, and with it sudo. After such a change, test in a new session before closing the old one. A new group shows in `id` only after a new login. `id makilele` reads `/etc/group` and shows it at once.
- `umask 027` in `.bashrc` worked for `sudo -iu dba_test` (a login shell), but `sudo -u dba_test bash -c umask` still gave `0022`. Services started by systemd do not read `.bashrc` either.
- `cp` of a `600` file into `/srv/dba` gave an ACL mask of `---`, so the group could not read it, although the default ACL says `rwx`. `cp` asks for the source's mode, and its group bits become the mask. On a file with an ACL, `chmod g+rw` sets the mask.
- `mv` keeps the owner, group and mode, so a moved file gets neither the group `dba` nor the ACL.
- After `userdel -r`, the user's files outside the home keep its UID (1001). The next new user would get the same UID and own them. `find / -xdev -nouser` finds them. In `/var/tmp` (sticky bit) only root could delete the leftover file.
