# 2026-09-29: Clones db1 and db2

I cloned db1 and db2 from `rhel-base`, and each got its own hostname, machine-id, SSH host keys and subscription. They start with the NUC, shut down cleanly with it, and find each other by name. One reboot stopped at the `grub>` prompt, most likely because a Cockpit console was open.

Phase 0 · Docs: [Clones](../architecture/vms.md#clones) · Runbook: [Clone a VM from the base image](../runbooks/clone-a-vm.md)

## What I did
- Added DHCP reservations for db1 (`.11`) and db2 (`.12`), cloned both with `virt-clone` and gave them 3 GB RAM.
- In the serial console, before the first SSH login, gave each clone its own hostname, machine-id and host keys.
- Added db1 and db2 to `~/.ssh/config`: one shared block and one small block per host.
- Registered and updated both VMs. machine-id, SSH fingerprint and subscription differ on all four hosts.
- `getent hosts db2` on db1 returns `.12`. The names come from the DHCP reservations.
- Turned on autostart for db1 and db2 and rebooted the NUC. Both came back with the same IPs and no new SSH prompts.
- Turned on `libvirt-guests`, so db1 and db2 shut down cleanly with the NUC.

## What broke
- **After the update and reboot, db1 stopped at `grub>`.** A Cockpit serial console was open and most likely answered GRUB's terminal queries. `normal` continued the boot.
- **Deleting only the ed25519 host key is not enough.** All three key pairs (`ssh_host_*`) must go.
- **`setmem --config` did not change the RAM after a reboot.** A reboot inside the guest keeps the same QEMU process, so it needs `virsh shutdown` and `virsh start`.
- **`sudo -rm ...` deleted nothing.** sudo read `-r` as its own option.
