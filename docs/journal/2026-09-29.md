# 2026-09-29: Clones db1 and db2

## What I did
- Added DHCP reservations for db1 (`52:54:00:00:00:11` → `.11`) and db2 (`52:54:00:00:00:12` → `.12`) to the libvirt `default` network.
- Cloned db1 and db2 from `rhel-base` with `virt-clone` and set their RAM to 3 GB with `setmaxmem` and `setmem --config`.
- In the serial console, before the first SSH login, gave each clone its own hostname, machine-id and SSH host keys. After the reboot I compared the key fingerprint from the console with the one in the first SSH prompt.
- Added db1 and db2 to `~/.ssh/config`: one shared block with the user, key and `ProxyJump nuc`, and one small block per host with its `HostName`.
- Registered both VMs and updated them to the latest kernel. Updated the NUC too.
- Checked that machine-id, SSH fingerprint and subscription identity are different on nuc, rhel-base, db1 and db2.
- The VMs find each other by name: `getent hosts db2` on db1 returns `.12`. The names come from the DHCP reservations.
- Turned on autostart for db1 and db2 (not for rhel-base), rebooted the NUC and checked: both VMs running, same IPs and hostnames, 3 GB RAM, registered, no new SSH prompts.
- Turned on `libvirt-guests` on the NUC, so db1 and db2 shut down cleanly when the NUC shuts down. Tested it by stopping the service by hand.

## What broke and how I fixed it
- `virsh net-update` takes an XML fragment in quotes (`"<host mac=... name=... ip=.../>"`), not options like `--mac`. The network name must come first, because virsh reads the arguments by position.
- `sudo -rm ...` deleted nothing. sudo read `-r` as its own option. The command is `sudo rm`.
- Deleting only the ed25519 host key is not enough. All three key pairs (`ssh_host_*`) must go.
- The new machine-id is the VM UUID without dashes. In a KVM guest, `systemd-machine-id-setup` takes it from the SMBIOS UUID, so it is still unique per clone.
- After the update and reboot, db1 stopped at the `grub>` prompt. A Cockpit serial console was open during the reboot and most likely answered GRUB's terminal queries. `normal` continued the boot, and the next reboot with no console open was fine.
- Only one console session per VM is allowed. `Active console session exists` means it is open somewhere else, for example in Cockpit.
- `setmem --config` on a running VM changes only the saved config. A reboot inside the guest keeps the same QEMU process, so the VM needs a full shutdown and `virsh start`.
- `/etc/nsswitch.conf` is generated by authselect. Do not edit it by hand.
- `/etc/sysconfig/libvirt-guests` does not exist on RHEL 10. The unit loads it as optional (`EnvironmentFile=-...`), and the defaults are in `man libvirt-guests`. The default `ON_SHUTDOWN=suspend` also shows as `shut off` in `virsh list`. Only the log (`journalctl -u libvirt-guests`) or `uptime` in the VM shows which one happened.
- `ssh db1` works from the desktop but not from the NUC. The desktop gets the IP from `~/.ssh/config`. The NUC asks the home router for DNS, not the libvirt dnsmasq.
