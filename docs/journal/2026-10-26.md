# 2026-10-26: Point-in-time recovery: WAL archiving to db2, a base backup, a timed restore

## What I did
- Turned on WAL archiving on db1 (started yesterday): `archive_mode = on` and an `archive_command` that copies every full 16 MiB segment to `/mnt/db2/backup/pgsql/wal` on db2 and never overwrites one that is already there. `archive_mode` needed a restart, `archive_command` only a reload; `pg_settings.context` tells which.
- SELinux blocked the archiver: `postgresql_t` may not use files labeled `nfs_t`, and no boolean allows it. I put only `postgresql_t` in permissive mode for one archive run, let `audit2allow` write the rules, added `read` for restores and loaded them as the local module `pg_archive_nfs` (in `selinux/`). Then back to enforcing.
- Took a base backup with `pg_basebackup -Ft -z -X stream -c fast`: 32 MB of data, 4.3 MB compressed, 1.3 s. `pg_verifybackup -n` checked it against the manifest.
- Shut down db2 while db1 wrote three segments. The database kept working, the archiver waited on the `hard` NFS mount, and all three segments were archived 10 seconds after db2 was back.
- Created a test table, wrote down the time, added one more row and dropped the table. Then I restored db1 in place to that time: moved the broken cluster to `data-broken`, extracted the base backup, set `restore_command`, `recovery_target_time` and `recovery_target_action = 'pause'`, and started the server with `recovery.signal`.
- It replayed 8 segments in 0.67 s and paused 4 seconds before the extra row. I checked the data while it was read-only (1000 rows, no extra row, `lab.items` unchanged), then promoted with `pg_wal_replay_resume()`. The server now runs on timeline 2.
- The whole outage, from `systemctl stop` to promote, took 9 min 31 s. Almost all of it was me typing.
- Removed the recovery settings with `ALTER SYSTEM RESET`, added `checks/13-pitr.sh` and ran it after a reboot of both hosts. With the SELinux module disabled, exactly 2 checks fail.

## What broke and how I fixed it
- I copied a placeholder from a table into `archive_command`. The shell read `<…>` as a redirect, the command failed and `failed_count` grew. Nothing is lost when archiving fails: the segment waits in `pg_wal` with a `.ready` file. The real path and a reload fixed it.
- `pg_verifybackup` needs `pg_waldump`, which is in `postgresql18-contrib`. A tar backup also needs `-n`, because `pg_waldump` cannot read WAL inside a tar file.
- My first db2-down test showed nothing, because I skipped the step that writes WAL. An idle database archives nothing: only a full segment or `pg_switch_wal()` sends one.
- A `hard` NFS mount hides an outage: the archiver just waits, so `failed_count` does not change. Monitoring has to watch the age of `last_archived_time` and the number of `.ready` files. A long outage would fill `/pgdata`.
- `journalctl -k` showed both `still trying` and `timed out` for db2. `still trying` was the `hard` request that waits (the archiver's `cp`); `timed out` were background requests.
- The restore log had `cp: cannot stat` lines for `00000002.history` and for the segment after the end of the archive. They are normal: recovery asks for files that may not exist.
- The target cuts off everything after it: a good row I added 4 seconds after the target was lost with the drop. In a real incident I would find the exact time of the bad commit with `pg_waldump`.
- After I enabled the SELinux module again, the checks still failed twice: the archiver waits 60 seconds after three failed tries. A minute later everything passed.
