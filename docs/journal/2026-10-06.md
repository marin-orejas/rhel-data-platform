# 2026-10-06: Backups with pg_dump, a systemd timer and cron

## What I did
- Created the test database `lab` with the table `items` (10,000 rows) and noted its fingerprint: `count(*)` 10000 and `sum(id)` 50005000.
- Created `/srv/backup/pgsql` (`postgres:dba`, `2750`). With `umask 027`, the group `dba` can read the backups but cannot delete them.
- Made a backup by hand first: `pg_dump | gzip` for one database, `pg_dumpall --globals-only` for the roles, and `tar -cjf` for the four config files. Installed `bzip2`, which the minimal install does not have.
- Wrote `pg-backup.sh` by hand on db1, one part at a time: arguments and checks (`$1`, `${2:-7}`, `test`), a loop over the databases (`for` with `$(psql -Atc ...)`), error handling (`set -o pipefail`, a failure counter, removing half-written files), the roles and config files, and deleting backups older than 7 days with `find -mtime -delete`.
- Tested every branch: no argument, a missing directory, no write permission, no server (`PGPORT=5999`), a database that does not accept connections (`ALTER DATABASE lab ALLOW_CONNECTIONS false`), and old files made with `touch -d '10 days ago'`.
- Restored the dump of `lab` into a new database with `psql -v ON_ERROR_STOP=1`. The fingerprint matched.
- The repo version of the script follows the style of the check scripts. I compared it with my working version with `diff`, installed it with `install` and ran all tests again.
- Added `pg-backup.service` (oneshot, `User=postgres`) and `pg-backup.timer` (every day at 02:00, `Persistent=true`). Tested a real trigger with a temporary `systemctl edit` override every 2 minutes, removed it with `systemctl revert`, and rebooted db1.
- Ran the same backup from the crontab of postgres every 2 minutes to compare, then removed it.
- Swapped phases 2 and 3 in the roadmap: RHCSA practice and the exam now come before replication and ETL.
- Added `checks/09-backup.sh`.

## What broke and how I fixed it
- Without `set -o pipefail`, a failed `pg_dump` still gave exit 0. gzip compressed the empty input into a 20-byte file that looked like a backup.
- `if` runs its block when the condition is true, so the condition has to describe the bad case. I first had `-d` and `-w` without `!`, and then added a `!` to `-z`, which did not need one.
- `[ "$failed" -gt 0]` without a space before `]` printed `[: missing ']'`, and the script ended with exit 0 after a failure. `bash -n` did not catch it: it checks the syntax, not whether a command works. Only the failure test showed it.
- An unquoted empty variable disappears from the command, and `test` gives a wrong answer without any error. Variables always go in quotes.
- `sudo -u`, cron and systemd do not read the `.bash_profile` of postgres, so psql looked for the socket on port 5432. The script now sets `PGPORT=${PGPORT:-5433}` itself.
- Run from my home directory, `find -delete` deleted the file but failed with `Failed to restore initial working directory`. `sudo -u` keeps the current directory, and postgres cannot enter `/home/makilele`. `cd /` at the start of the script fixed it.
- tar without `-C` would archive the whole data directory. A copy of the data directory of a running server is not a valid backup.
- A failed `tar -cjf` (no bzip2 yet) still left an empty archive behind. Every step that fails has to remove its own file.
- `-c ON_ERROR_STOP=1` made psql run `ON_ERROR_STOP=1` as SQL. `-c` takes SQL and `-v` takes a psql variable.
- After I moved the timer from 18:00 to 02:00, its `Description=` still said 18:00. A time in the description goes stale, so I took it out.
- `journalctl -u crond` showed nothing about the cron jobs, but `journalctl -t CROND` did. On RHEL 10, cronie writes the job output to the journal (`CMDOUT`), but not the exit code.
- `crontab -r` sits next to `-e` on the keyboard and deletes the whole crontab without asking. cronie 1.7 keeps a copy in `/root/.cache/crontab/`.
