# 2026-11-17: Kubernetes app settings and in-cluster traffic

I wanted the app to take its settings from outside the image, and then the pods to reach it by a name. Now the page and `APP_RELEASE` come from a ConfigMap built by Kustomize, and a client pod gets release 3 from `http://web.web`. A network policy lets only the client in: a pod with the same label from the namespace `default` got `000` after 5 s. In etcd I found the Secret's token in plain text, and a NodePort answered on k8s1, where firewalld has no NodePort range open.

## What I did
- Put my page and `APP_RELEASE` into the ConfigMap `web-config`. `/` now gives `200` with the page instead of `403`.
- Changed the ConfigMap: the page in the running pod after 53 s, `APP_RELEASE` only after `kubectl rollout restart`.
- Made the Secret `web-token` by hand from `openssl rand -hex 32`. The pods get it as `APP_TOKEN` and `/etc/web/token`.
- In etcd `grep -c` for the token gave `1`. No encryption at rest, so only RBAC guards it, and the default service account gets `no`.
- Kustomize builds the folder now. The generated ConfigMap is `web-config-kk6kk2847d`, with a hash of its content in the name.
- Release 3 rolled out with no restart, because the new name went into the pod template.
- `apply -k` left the old ConfigMaps, so I deleted them. A `rollout undo` to revisions 1–9 would now give pods that don't start.
- Check 28 has 20 checks. A `kubectl patch` of `APP_RELEASE` to `4` gave one FAIL, and checks 25–28 passed after a reboot.
- Gave `web` a Service on `10.110.25.239`. On k8s2 it is one nftables rule that picks a pod by `numgen random mod 2`.
- A test NodePort answered from nuc on k8s2 and k8s1, though only the workers open `30000-32767/tcp`. I deleted it.
- The client is the web image with `sleep infinity` in its own namespace. It already has `curl` and `getent`.
- From the client `web.web` gives the ClusterIP. Plain `web` gives exit 2: the pod searches only its own namespace.
- Both CoreDNS pods run on k8s1, so the cluster has no DNS while k8s1 reboots.
- After the default deny alone the client got `000` after 5 s. The web pods stayed `1/1`: probes come from the node.
- `allow-client` matches the namespace and the label in one `from` element. The client got `200`, the two test pods `000`.
- Patching the port of `allow-client` to `8081` failed exactly one of the 13 checks in check 29. After a reboot 25–29 passed.

## What broke
- **Check 28 passed with no pods at all.** When `kubectl get pods` returned nothing, the loop over the pods ran zero times and had nothing to fail. Now it first checks that the pod count equals `spec.replicas`.
- **`kubectl auth can-i … --as=system:serviceaccoutn:web:default` said `no`, and I took it as the answer.** The name was misspelled. Kubernetes has no user objects, so `--as` takes any string, and a user nobody knows can do nothing. A `no` proves something only for the right name.
- **`git diff` printed nothing for the new `configmap.yaml`.** The file was never `git add`ed, and `git diff` compares with the index. `kubectl diff -f` compares the file with the cluster.
- **`kubectl get configmap -n kube-system -o jsonpath='{.data.Corefile}'` printed nothing.** Without a name kubectl returns a List, which has no `.data`, and jsonpath prints nothing for a missing key, with no error. I ran it three times before I added the name `coredns`.
