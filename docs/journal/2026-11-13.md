## What I did
- `site.yml` imports the six playbooks in build order. `bootstrap.yml` makes the `ansible` user, with my own login and `-K`.
- Moved `/srv/dba` into the role `base` and the nightly dumps into a new role `pgdump`. Both backup units retry now.
- GitHub Actions runs the syntax check and `ansible-lint` on every push to `ansible/`. 18 findings first, then `production`.
- New system disks for db1 and db2 from `rhel-base`, with the old MACs. The data disks went back as `vdb`, and both run RHEL 10.3.
- The first `site.yml` built db1 from its data disk in 3 min 46 s (`changed=49`). After two fixes, `changed=0` in 1 min 38 s.
- The restore test gave the same sums on the copy and the standby. After a reboot, all checks 05 to 24 passed.
- The archive by hand went with db2's old file system, so I dropped it. Checks 13 and 23 read the pgBackRest archive now.
- Deleted the old system disks. The pool has 25.86 GiB free for k8s1–k8s3.

## What broke
- **On db2 the storage role said `changed`, and then `pg_basebackup` ran on a disk that held a standby.** The clone's LVM devices file listed only `vda3`, so the LVs on `vdb1` were inactive and blivet saw no file system: it ran `mkfs.xfs -f` on both, safe mode or not, and every backup went with them. The storage play now imports and activates the VG, and stops on an inactive LV.
- **PostgreSQL on db2 failed with `could not access directory "/pgdata/pgsql/data": Permission denied`.** The new XFS was `unlabeled_t`. The `semanage fcontext` rule was there, but nothing ran `restorecon` after `mkfs`, and the storage play runs it now.
- **Archiving on db1 failed 270 times with `[103]: unable to find a valid repository`.** The role made the repository directory but never the stanza, and in lesson 23 it had found one ready. WAL waited in `pg_wal`, so nothing was lost, and the role runs `stanza-create` now.
- **The nightly dump had failed at every boot since 2026-11-10 with `hostname lookup for db2 failed`.** The hosts run only in the evening, so 02:00 never came, and `Persistent=true` caught up at boot before the share on db2 was up. Both units retry a minute apart now, and at the reboot both caught up on the first try.
