# 2026-11-24: An S3 object store on db2 and CloudNativePG backups

Garage v2.5.0 runs on db2 now, on a 5 GiB disk of its own behind nginx with TLS, and a 16 MiB PUT from k8s2 came back `200`. Before one SELinux boolean, the same PUT gave `502`, after nginx had already taken all 16777216 bytes. Then `pg` started to back itself up there, and a restore to a set time put all 5,000 dropped rows back into `pg` in 1 s.

## What I did
- Gave db2 a third disk, `vdc`, 5 GiB thin, with the VG `objects` and an XFS volume on `/srv/garage`.
- Installed Garage v2.5.0 as `garage.service`, only on `127.0.0.1`, with the bucket `pg-backups` and the key `cnpg`.
- I pasted the first secret of `cnpg` by mistake, so I deleted the key and made a new one.
- Signed a certificate for `db2` and `192.168.122.12` with the lab CA and put nginx on port 443 in front of Garage.
- From k8s2 `openssl s_client` said `Verification: OK`, and a PUT, a list and a GET worked over both names.
- Copied db2's two data disks with `virsh vol-clone` before the role's first run. I deleted the copies at the end.
- The role `garage` keeps five values in Vault. Its first run changed one line: fstab mounts `/srv/garage` by UUID now.
- Check 33 ends with a signed PUT, GET and DELETE from k8s2, with the key taken from the vault. It passed.
- Installed plugin-barman-cloud v0.16.0 with Helm next to the operator, and an ObjectStore `db2` for `https://db2`.
- Added the plugin to the Cluster `pg`. Both pods were made again with a sidecar, the standby first.
- The first WAL reached the bucket at 18:56:21Z. An idle 16 MiB segment is about 17 kB there after gzip.
- `pg-nightly` runs at 02:00 UTC. The first two backups ran on the standby `pg-1`, 13 s and about 4.2 MB each.
- Made `restore_test` with 5,000 rows, took `now()`, dropped the table 10 s later and switched the WAL.
- Restored `pg-restore` to that time. Its history file says it stopped `before 2026-11-24 20:55:01.870643+00`, the DROP.
- `pg_dump -t restore_test | psql` into `pg-2` gave `COPY 5000` and the same `sum(id)`. `delete -k` removed `pg-restore`.
- Check 34 reads the bucket from k8s2 with a signed list, and it passed on its first run.

## What broke
- **nginx answered `502`, and `error.log` said `connect() to 127.0.0.1:3900 failed (13: Permission denied)`.** SELinux does not let nginx (`httpd_t`) connect to `unreserved_port_t`, and 3900 is one. `setsebool -P httpd_can_network_connect on` fixed it. `audit2why` also offered `nis_enabled`, which opens those ports to many other services too.
- **The signed requests gave `403 AccessDenied Forbidden: No such key: ` three times, with an empty key name.** I had run `ssh db2 read -rp 'Key ID: ' …` from the desktop. The quotes were lost, the second `read` ran on the desktop, and curl ran later in a new session with empty variables.
- **`curl -T --cacert ~/lab-ca.crt` failed with `curl: (3)`.** `-T` took `--cacert` as its upload file, and the CA path became a URL. An option that takes a value eats the next word.
- **No WAL went to the bucket for 71 minutes, on a healthy cluster.** With no writes there is no WAL, and `archive_timeout` switches a segment only after some activity. So `Last Archived WAL` can be hours old, and check 34 does not expect a recent one.
