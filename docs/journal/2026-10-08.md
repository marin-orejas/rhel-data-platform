## What I did
- Ran a drill for the RHCSA storage objectives on db2. I started on the evening of 2026-10-07 and finished today. At the end I removed everything, so db2 is back to the state in `architecture.md`.
- Kept the drill inside a budget: VG `data` on db2 had 7164 MiB free, and 5 GiB of it stays reserved for the replica in phase 3, so I had 2044 MiB. I did not touch LV `backup`.
- Created LV `scratch` (1 GiB) with ext4 and the label `scratch`, and mounted it on `/mnt/scratch` with `LABEL=scratch` in fstab. The last field is `2`, so systemd runs fsck on it at boot; for XFS it is `0`. I wrote a 200 MiB test file and saved its checksum outside the LV.
- Grew `scratch` to 1.5 GiB with `lvextend -r` while a shell was inside `/mnt/scratch`. ext4 grows online, like XFS.
- Shrank it back to 1 GiB. `lvreduce` without `-r` refused, because the file system was bigger than the new size. `lvreduce -r` asked before it unmounted, then ran `e2fsck`, `resize2fs`, reduced the LV and mounted it again. The file system shrinks first and the LV second, the reverse of growing. The checksum still matched.
- Created LV `swaptest` (512 MiB), ran `mkswap`, added it to fstab by UUID and turned it on with `swapon -a`. `swapon --show` listed it next to the 2 GiB `rhel/swap`, with a lower priority.
- Made a VG that is really full: a temporary 1 GiB disk (`vdc`) as a whole-disk PV, VG `exam`, and LV `docs` with `-l 100%FREE`, XFS on `/mnt/docs` by UUID. `lvextend -L +512M exam/docs` failed with `Insufficient free space: 128 extents needed, but only 0 available`.
- Fixed it the way I would on a real server: a second temporary disk (`vdd`), `pvcreate`, `vgextend exam /dev/vdd`, then `lvextend -r -L +512M exam/docs`. The LV now spanned two disks, and `lsblk` showed `exam-docs` under both.
- Attached both temporary disks with `--live --config`, because a VG that loses a PV after a reboot cannot activate the LVs on it. Before the reboot, `virsh domblklist db2 --inactive` showed both disks in the saved config.
- Rebooted db2, like an exam grader would, and checked both mounts, both swaps, `pvs`, the checksum and `systemctl --failed` (0 units). Checks 07, 08 and 10 passed on db2.
- Cleaned up in reverse order: unmount or `swapoff`, remove the fstab line, `lvremove`, `vgremove exam`, `pvremove`, and on the NUC `virsh detach-disk --live --config` and `virsh vol-delete`. In VG `data` I removed only the two drill LVs. After another reboot, fstab had its 5 original lines, `findmnt --verify` showed no warnings, and checks 07, 08 and 10 passed.
- In the afternoon I started break and fix on db2, the last item of phase 1. Root is locked on the VMs (`rootpw --lock` in the kickstart, `passwd -S root` shows `L`), so all admin work goes through `sudo`.

Emergency mode asks for the root password, and with a locked root it gave me no shell. After Enter the boot went on, and SSH worked in the same boot. The edit was only for that one boot.

## What broke and how I fixed it
- I forgot `mkfs.xfs` on `exam/docs`, ran `blkid` without sudo, and copied a UUID from its short list into fstab. It was the LVM PV UUID of `/dev/vda3`, the system disk. `mount -a` failed with `/dev/vda3: Can't open blockdev`, because device-mapper keeps the PV open, so nothing was written to it. After a reboot, this line would have put db2 into emergency mode. I made the file system, asked for its UUID directly with `sudo blkid -s UUID -o value /dev/exam/docs`, and fixed the line.
- The three kinds of UUID in my fstab look different. A file system UUID is 8-4-4-4-12 hex characters. An LVM PV UUID is 6-4-4-4-4-4-6 mixed-case characters and never goes in fstab. The FAT UUID of `/boot/efi` is 4-4.
- Not every `findmnt --verify` warning is harmless. Two swap lines give `none … target specified more than once`, which means nothing. `xfs does not match with on-disk LVM2_member` meant the line pointed to the wrong device.
- I skipped `mount -a` after the fix, and `df -h /mnt/docs` showed `/dev/mapper/rhel-root`. On a directory that is not a mount point, `df` shows the parent file system. Files written there would land on the root file system and be hidden by the later mount. This is why `postgresql.service` has `RequiresMountsFor=/pgdata`.
- `restorecon` printed nothing until the new file system was mounted: a plain directory under `/mnt` already has `mnt_t`, and only the root of a new file system is `unlabeled_t`. `lost+found` on the ext4 stayed `unlabeled_t`, because the policy has `<<none>>` for everything below `/mnt/*/`.
- `lvreduce -r` asks `Continue with ext4 file system reduce steps: unmount, fsck, resize2fs? [y/n]`. That question is safe. The dangerous one, on older RHEL without `-r`, is `Do you really want to reduce …? THIS MAY DESTROY YOUR DATA`. A shell inside the mount point blocks the unmount; `fuser -vm /mnt/scratch` showed my `bash` with `c` (current directory).
- `lvcreate` takes only the VG, because the LV does not exist yet and its name goes in `-n`. `lvs`, `lvextend`, `lvreduce` and `lvremove` take `VG/LV`.
- Editing a boot entry in GRUB over the serial console (`virsh console`) did not work: the screen was garbled, keys landed in the wrong place, and once the boot stopped at the `grub>` prompt. The VNC console worked.
- I wanted a second console and ran `grubby --update-kernel=ALL --args="console=tty0"`. It replaced `console=ttyS0,115200` instead of adding to it, because grubby first removes every argument with the same name, and the serial console lost its login prompt. Several `console=` arguments must go in one call: `--args="console=ttyS0,115200 console=tty0"`. The last one becomes `/dev/console`, where the emergency shell and the `rd.break` shell appear.
- Right after that fix, `virsh console` still showed no login, because I had not rebooted. `grubby` only writes the files, and the running kernel keeps its command line.
- A VGA card is a classic PCI device, so libvirt had added a `pcie-root-port` and a `pcie-to-pci-bridge` for it on the q35 machine. Removing `<graphics>` and `<video>` with `virsh edit` left both behind. I compared the PCI controllers with db1, which never had VNC (`diff` of both `virsh dumpxml --inactive`), checked that no device used their buses, and removed them. A reboot from inside the guest keeps the same QEMU process, so the change needed `virsh shutdown` and `virsh start`.
