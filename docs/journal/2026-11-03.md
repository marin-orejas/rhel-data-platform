# 2026-11-03: PostgreSQL config files from templates

I wanted Ansible to write `postgresql.conf` and `pg_hba.conf`, with a reload and a dry run before each change. Both files now come from templates on db1 and db2, and check 20 passes 20 of 20 after a reboot of both hosts. The first `pg_hba.conf` run cut every new login from the network: I had named the list wrong, and the dry run showed it in six `-` lines I did not read.

Phase 4 · Docs: [Role postgresql](../architecture/ansible/postgresql.md), [PostgreSQL server](../architecture/postgresql/server.md), [pgBackRest](../architecture/backups/pgbackrest.md) · Runbook: [Build a standby](../runbooks/build-a-standby.md) · Checks: [20](../../checks/20-postgresql-templates.sh)

## What I did
- The first dry run of the `postgresql.conf` template showed 889 lines. The new file has 24: the `initdb` values and mine.
- Five of my settings were also in `postgresql.auto.conf` from `ALTER SYSTEM`, and that file wins. I reset them one by one.
- After the reset `pg_settings` showed the same values, now from `postgresql.conf`, and `pgbackrest check` passed. No restart.
- `pg_hba.conf` is now a list: the six `initdb` lines in the role, my six in `group_vars`. Both hosts get the same file.
- `log_line_prefix` adds `user@database` to every log line. A reload was enough.
- `max_connections = 150` in `group_vars` stopped the run at the settings check, and the server stayed on 100. Then I put 100 back.
- Added `checks/20-postgresql-templates.sh`. A `work_mem` line from `ALTER SYSTEM` failed one check, but the playbook's own check missed it.
- The standby runbook's `tee -a` and `ALTER SYSTEM` steps would now fight the role, so I took them out.

## What broke
- **`FATAL: no pg_hba.conf entry for replication connection from host "192.168.122.12", user "replicator"`** I named the list `postgresql_hba_extra_settings`, the template reads `postgresql_hba_extra_rules`, and the empty default in the role won without a warning. The dry run had it (`@@ -1,128 +1,7 @@`), and the walreceiver kept streaming only because `pg_hba.conf` is read when a connection opens.
- **`max_connections|setting could not be applied`, in a dry run on db1.** I had set 150 with `ALTER SYSTEM`, which only writes `postgresql.auto.conf`. At the next reboot db1 would have started with 150 next to a standby on 100, and a standby needs at least the primary's value. `ALTER SYSTEM RESET max_connections` took it out.
