# 2026-10-01: Data disk for db1

## What I did
- Created `db1-data.qcow2`, a 10 GiB thin qcow2 volume in the `default` pool, and attached it to the running db1 as `vdb` with `virsh attach-disk --subdriver qcow2 --live --config`.
- In db1, created a GPT partition table and one Linux LVM partition with `fdisk`. Then created PV `/dev/vdb1`, VG `data` and LV `pgdata` (5 GiB). The other 5 GiB stay free, so I can practise extending the LV later.
- Made an XFS file system with the label `pgdata`, created `/pgdata` and added it to `/etc/fstab` by file system UUID. Tested the entry with `systemctl daemon-reload`, `mount -a` and `findmnt --verify` before any reboot.
- Rebooted the NUC. libvirt-guests shut down db2 and db1 cleanly. Both VMs came back with `/pgdata` mounted, and all three hosts kept the logs from earlier boots.
- Added `checks/05-storage.sh`. It runs on db1 over SSH (`ssh db1 bash -s < checks/05-storage.sh`) and needs no sudo.

## What broke and how I fixed it
- My first volume was raw, although its name ended in `.qcow2`. The file name does not set the format, `--format` does. I deleted the volume and created it again with `--format qcow2`.
- `attach-disk` needs the format too (`--subdriver qcow2`). Without it, libvirt treats the disk as raw.
- `attach-disk --config` alone changes only the saved config. For a running VM that must see the disk now and after a restart, use `--live --config`.
- The disk names in libvirt are only hints for the guest. The CD-ROM is `sda` in libvirt but `sr0` in db1. Names like `/dev/vdb1` can change, so fstab uses the UUID.
- There are three different UUIDs: the file system UUID, the LV UUID and the PV UUID. fstab needs the file system UUID from `blkid`. Without sudo, `blkid` shows only cached devices and missed the new file system.
- `journalctl -b 1` is the first boot in the journal, not the previous one. The previous boot is `-b -1`.
